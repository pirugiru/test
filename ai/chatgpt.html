이 차이를 이해해야 “만들 수 있는 것”과 “만들 가치가 있는 것”을 구분할 수 있습니다.

가장 먼저 바로잡기

LLM과 ChatGPT는
같은 말이 아닙니다.

🧠

LLM

사람의 말을 이해하고 만들어 내는 핵심 AI 엔진입니다.

+
🧰

ChatGPT·Claude 같은 서비스

LLM에 파일, 검색, 프로젝트, 앱 연결, 작업 도구를 붙인 완성된 제품입니다.

그래서 “최신 LLM이 Agent가 되었다”기보다 “최신 AI 서비스가 매우 agentic해졌다”가 더 정확합니다.

용어 지도

먼저 이 여섯 단어의
자리를 잡겠습니다.

Prompt지금 하는 부탁
Instructions늘 지킬 업무 규칙
Knowledge찾아볼 공식 자료
Tool사용 가능한 도구
Action도구로 하는 행동
Agent이것을 묶은 담당자

지금 외울 필요는 없습니다. 다음 장부터 하나씩 비유로 설명합니다.

용어 ①

Prompt

지금 AI에게 하는 부탁

그때그때 달라집니다.

사용자가 대화창에 입력하는 질문, 요청, 작업 지시입니다.

예: “이 교육과정 PDF를 읽고 핵심 차이 세 개를 알려줘.”
용어 ②

Instructions

Agent가 늘 지켜야 하는 업무 규칙

매번 다시 말하지 않아도 됩니다.

Agent의 역할, 말투, 판단 기준, 금지 사항을 제작자가 미리 정합니다.

예: “반드시 학교 규정에서 근거를 찾고, 모르면 담당 부서를 안내한다.”

Instrument가 아닙니다. 연수에서 비슷하게 들렸다면, Microsoft 화면에서 주로 쓰는 용어는 Instructions(지침)입니다.

용어 ③

Knowledge

답할 때 찾아볼 공식 자료

AI의 머릿속에 새로 외우게 하는 것이 아닙니다.

질문이 들어오면 연결된 문서·사이트·데이터에서 관련 근거를 찾아 답에 사용합니다.

비유: 담당자 책상 옆에 놓인 ‘공식 서가’
용어 ④·⑤

Tool & Action

도구와, 그 도구로 하는 실제 행동

Tool

메일·목록·일정·업무 시스템에 연결된 사용 수단입니다.

Action

그 Tool을 이용해 조회·등록·전송·수정하는 실제 동작입니다.

예: 메일 Tool을 사용해 담당자에게 접수 알림을 보내는 것이 Action입니다.
용어 ⑥

Agent

특정 일을 맡도록 구성한 AI 담당자

LLM

+ Knowledge
+ Tools / Actions

사용자가 Prompt로 일을 부탁하면, Agent는 정해진 규칙과 자료·도구를 이용해 처리합니다.

새 장 · Agent와 Agentic

비슷하게 들리지만
하나는 대상, 하나는 방식입니다.

Agent = 명사

특정 일을 맡도록 지침·자료·도구를 구성해 놓은 AI 담당자 또는 시스템

Agentic = 형용사

목표를 위해 스스로 계획하고 도구를 고르며 여러 단계를 이어 가는 ‘Agent 같은 작동 방식’

비유: Agent는 ‘직원’, Agentic은 ‘주도적으로 일하는 방식’입니다.
Agentic이란?

답만 말하지 않고
목표를 이루기 위해
여러 단계를 수행하는 것

① 계획하고

해야 할 일을 순서로 나눕니다.

② 자료와 도구를 고르고

파일·검색·앱 등 필요한 수단을 선택합니다.

③ 결과를 만들고 고칩니다

중간 결과를 확인하며 다음 단계를 이어 갑니다.

새 장 · 요즘 범용 AI

범용 AI는
한 가지 업무만을 위해
만든 AI가 아닙니다.

여러 종류의 일을 폭넓게 돕는 공용 작업 도구

질문 답변, 글쓰기, 요약, 파일 분석, 검색, 계획 수립처럼 사용자가 그때그때 부탁하는 다양한 일을 처리합니다.

ChatGPTClaudeGeminiCopilot

특정 학교 업무에 고정된 전용 Agent와 달리, 사용자가 매번 Prompt와 자료를 주며 방향을 잡습니다.

요즘 범용 AI ①

파일을 올려 주면
그 자료를 읽고 일합니다.

PDF 8개 비교
→ 핵심 차이 정리
→ 협의 자료 초안

이 정도의 Knowledge 활용은 새 Agent를 만들지 않아도 가능합니다.

요즘 범용 AI ②

프로젝트에 자료와 지침을
계속 보관할 수도 있습니다.

ChatGPT Projects

대화·업로드 파일·프로젝트 지침을 한곳에 모아 반복 작업에 사용합니다.

Claude Projects

프로젝트별 지식 자료와 지침을 두고 관련 대화를 이어 갑니다.

기능과 제공 범위는 요금제·학교 계정 정책에 따라 달라질 수 있습니다.

검색 · 파일 생성 · 앱 조회 · 웹 작업

허용된 도구와 권한 안에서 여러 단계를 실행하는 기능이 이미 일반 AI 서비스에 들어오고 있습니다.

이제 “일반 AI는 말만 한다”는 설명은 정확하지 않습니다.

범용 Agentic AI

“지금 내가” 일을
시키는 개인용 작업대

사용할 때마다 내가 정합니다.

목표를 말하고, 파일을 올리고, 결과를 보며 수정 지시를 합니다.

유연하고 빠릅니다. 혼자 하는 비정형 업무에 특히 편합니다.

Agent Builder로 만든 Agent

“여러 사람이” 같은 방식으로
쓰는 업무 서비스를 만듭니다.

제작자가 미리 정합니다.

역할, 지식, 사용할 도구, 권한, 대화 흐름, 배포 대상과 관리 방법을 구성합니다.

한 번 잘 만들어 여러 사용자가 반복해서 쓸 때 의미가 커집니다.

비유로 이해하기

범용 AI는
나와 일하는 유능한 비서

↕

전용 Agent는
업무 매뉴얼과 시스템을 가진 안내 창구

비서 한 명을 잘 쓰는 것과, 누구나 이용할 공용 업무 창구를 만드는 것은 목적이 다릅니다.

Microsoft 용어 주의

연수에서 말하는 도구도
두 수준이 있습니다.

M365 Copilot의 Agent Builder

개인·소규모 팀이 조직 콘텐츠 중심의 가벼운 Agent를 빠르게 만듭니다.

Copilot Studio

더 넓은 배포, 복잡한 흐름, 커넥터, 분석과 조직 통제가 필요한 Agent를 만듭니다.

이 자료에서는 둘을 묶어 “Agent Builder로 만드는 전용 Agent”라고 설명하되, 복잡한 기능은 주로 Copilot Studio를 뜻합니다.

Agent Builder의 핵심

장점은 크게
두 가지입니다.

📚

Knowledge

승인된 자료에서 근거를 찾아 더 일관되게 답합니다.

⚙️

Action

연결된 시스템을 조회하거나 실제 업무를 실행합니다.

Knowledge

정해 둔 “공식 서가”에서
답의 근거를 찾습니다.

질문
→ 관련 문서 검색
→ 근거를 넣어 답변

여러 사용자가 같은 규정·매뉴얼을 기준으로 답을 받아야 할 때 강합니다.

Knowledge의 현실

Agent가 알아서
진실을 만드는 것은 아닙니다.

자료가 낡으면

낡은 규정을 근거로 답할 수 있습니다.

자료가 충돌하면

어느 문서가 우선인지 정해야 합니다.

담당자가 없으면

신뢰할 수 있는 Knowledge도 곧 낡습니다.

Action

답변에서 끝나지 않고
시스템에 일을 시킵니다.

조회

“요청 처리 상태를 알려줘.”

등록·변경

“지원 요청을 접수하고 담당자에게 알려줘.”

이것이 단순한 파일 Q&A보다 Agent Builder가 강한 지점입니다.

하지만 Action에는

시스템으로 들어가는
“정식 다리”가 필요합니다.

커넥터 또는 API
+ 로그인·권한
+ 조직의 허용 정책

Agent에게 지시문만 써 준다고 학교 시스템을 조회하거나 수정할 수 있는 것은 아닙니다.

Agent Builder가 빛나는 조건

이 네 가지가
함께 있어야 합니다.

여러 사용자가

같은 Agent를 쓰고

같은 업무가

충분히 자주 반복되며

자료와 시스템이

정식으로 연결되어 있고

운영 책임자가

지식·권한·오류를 계속 관리해야 합니다.

기업에서 잘 맞는 예

직원 500명이 쓰는
IT 지원 Agent

Knowledge

공식 IT 매뉴얼에서 해결 방법을 안내합니다.

Action

해결되지 않으면 티켓을 만들고 담당 팀에 전달합니다.

한 번 만든 비용을 수백 명의 반복 사용으로 나눌 수 있습니다.
학교 업무의 현실 ①

많은 업무는
특정 선생님 한 명이 맡습니다.

사용자 수
1명

그 한 명이 자기 일을 편하게 하려고 별도 Agent를 만들면 제작·검증 시간을 나눠 가질 사용자가 적습니다.

학교 업무의 현실 ②

내가 떠난 뒤
후임자가 쓸지도 불확실합니다.

후임자가 같은 업무를 맡더라도

Agent Builder 사용 권한·계정·연수 경험이 없을 수 있습니다.

운영자가 사라지면

문서 갱신, 오류 수정, 권한 연결을 맡을 사람이 없어집니다.

“인수인계 자산”이 아니라 “전임자만 아는 시스템”이 될 수 있습니다.
사용 편의 차이

혼자 쓸 때는
ChatGPT·Claude가 훨씬 쉽습니다.

범용 AI

열기 → 파일 올리기 → 부탁하기 → 고치기

VS

전용 Agent

설계 → 지식 연결 → 지침 작성 → 테스트 → 배포 → 유지보수

개인 업무라면 작은 편의 때문에 큰 제작 과정을 떠안을 이유가 약합니다.

ROI 계산

절약 시간보다
만들고 유지하는 시간이 크면
손해입니다.

1회 절약 시간 × 반복 횟수 × 사용자 수

− 제작·검증·사용료·유지보수·위험 비용

학교의 1인 담당 업무는 특히 “사용자 수”와 “후속 운영 기간”이 작아지기 쉽습니다.

예: 나만 만드는 수업 자료

매번 내용과 판단이 달라지는 일은
전용 Agent보다 대화가 낫습니다.

더 단순한 방법

범용 AI에서 지난 프롬프트를 다시 쓰고, 이번 수업 파일을 올리고, 대화로 결과를 조정합니다.

전용 Agent 제작보다
좋은 프롬프트 하나가 경제적일 수 있습니다.
학교에서 Knowledge는?

대부분의 개인 활용은
이미 더 쉬운 방법이 있습니다.

한 번 쓸 자료

ChatGPT·Claude에 파일을 직접 올립니다.

계속 쓸 자료 묶음

프로젝트 기능이나 NotebookLM을 사용합니다.

즉 개인의 문서 기반 질문만으로는 Agent Builder의 추가 비용을 정당화하기 어렵습니다.

학교에서 Action은?

가장 큰 장점이지만
가장 막히기 쉬운 부분입니다.

내부망·외부망 분리

클라우드 Agent가 내부 시스템에 접근할 통로가 제한됩니다.

승인된 API·커넥터 부족

조회·등록에 필요한 정식 연결 수단이 없거나 개인이 만들 권한이 없습니다.

NEIS 등 특정 시스템의 실제 연결 가능성은 기관 정책과 제공 API를 개별 확인해야 합니다.

클라우드 업무 기반이 있다면

Teams·SharePoint·Gmail을
업무에 쓸 때는 이야기가 달라집니다.

자료가 이미 모여 있고

권한을 따라 필요한 Knowledge를 찾기 쉽습니다.

업무 앱이 이미 연결되어 있어

메일·목록·일정·승인 같은 Action을 이어 붙이기 쉽습니다.

Microsoft 환경에서는 “겁나 편한” 이유가 바로 이것입니다.
하지만 현재 학교는

그 기반을 조직적으로
사용하지 않는 경우가 많습니다.

Knowledge의 이점은
파일·프로젝트로 상당 부분 대체

Action의 이점은
시스템 장벽 때문에 제한

그래서 Agent Builder의 두 장점 중 학교에서 새롭게 얻는 실익이 작아질 수 있습니다.

따라서 현재의 결론

혼자 쓰는 학교 업무를
새 Agent로 만드는 것은
대체로 ROI가 낮습니다.

범용 AI가 더 쉽고

파일·프로젝트로 Knowledge 활용이 가능하며

전용 Agent의 Action은

학교 시스템과 연결하기 어렵고

후임자가 계속 쓴다는

운영의 연속성도 보장하기 어렵기 때문입니다.

그래도 검토할 수 있는 경우

개인이 아니라
“학교의 공용 서비스”일 때

4개 이상이라면 작은 시범 운영을 검토할 만합니다.
한 문장 결론

Agent Builder는
더 똑똑한 AI를 만드는 도구가 아니라,
조직의 지식과 행동을
공용 서비스로 고정·배포하는 도구입니다.

공용 사용자·연결된 시스템·지속 운영자가 없는 학교의 개인 업무라면, 최신 범용 Agentic AI를 직접 쓰는 편이 더 쉽고 경제적입니다.
